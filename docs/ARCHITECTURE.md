# Архитектура

## Текущий этап

Модульный монолит: один процесс FastAPI, React + TypeScript/Vite и SQLAlchemy. Нативный локальный запуск использует SQLite через `aiosqlite`; CI и необязательный Compose проверяют PostgreSQL 16. Backend применяет Alembic перед запуском. `/health/ready` выполняет `SELECT 1`; `/health/live` проверяет только процесс приложения. Frontend покрывает регистрацию и вход, поиск пользователей и чатов, личные и групповые чаты, историю, emoji-ввод, реакции, ответы и вложения, редактирование и удаление, статусы прочтения, mute и realtime-подключение с повторной отправкой ожидающих сообщений.

Реализованы Core, Auth, Users, Chats, Messages и Realtime. Users service ищет только активные профили без email и ограничивает частоту запросов. WebSocket принимает JWT первым событием, регистрирует соединение в process-local manager, сохраняет сообщения и расширенные события до подтверждения/рассылки текущим участникам чата. Вложения сохраняются на локальный диск; доступ проверяется по членству в чате. Прочтение хранится как курсор последнего просмотренного сообщения на участника. Сессии БД открываются для handshake и каждого события отдельно, не удерживая connection pool пока WebSocket простаивает.

## Целевая декомпозиция

Есть Core (конфигурация и БД), Auth, Users, Chats, Messages и Realtime. HTTP-обработчики вызывают сервисы; сервисы применяют бизнес-правила и работают через async SQLAlchemy с настроенной СУБД. WebSocket использует те же сервисы сообщений, что и HTTP/API-слой.

Сохранение сообщения должно завершить транзакцию до отправки `message.ack` и рассылки `message.new`. Настроенная БД остаётся источником истины; CI дополнительно проверяет транзакции на PostgreSQL. Менеджер соединений может держать только активные WebSocket-соединения в памяти одного процесса.

## План и риски

1. Инфраструктура (выполнено): Compose, конфигурация, API health, основа Alembic.
2. Auth (выполнено): Argon2id, JWT, уникальность в БД; риск гонок регистрации закрывается ограничениями БД и IntegrityError.
3. Chats (выполнено): участники, роли, канонический ключ direct-пары для защиты от дублей на уровне БД.
4. Messages (выполнено): идемпотентность, стабильная cursor-пагинация, поиск с проверкой членства.
5. Realtime (выполнено): аутентификация первым событием, протокол, лимиты; менеджер соединений локален процессу.
6. Frontend (выполнено): основные сценарии и восстановление WebSocket.
7. Качество (выполнено в CI): unit и integration тесты, Ruff, mypy, frontend build и npm audit; integration проверяется на PostgreSQL 16.

Отложены: LLM-суммаризация (до выбора провайдера), refresh-токены, межпроцессная рассылка WebSocket и брокер событий. Текущий read receipt хранит один курсор прочтения на пользователя в чате, а не отдельную запись на каждое сообщение.
