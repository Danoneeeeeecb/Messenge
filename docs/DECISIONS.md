# Архитектурные решения

## ADR-001: модульный монолит, SQLite локально и PostgreSQL в CI

- Статус: принято.
- Контекст: MVP должен демонстрировать границы модулей и транзакционное хранение без преждевременного распределения системы.
- Решение: один FastAPI backend, React frontend и async SQLAlchemy/Alembic. Для локальной работы используется SQLite; PostgreSQL остаётся целевой СУБД CI и Compose.
- Последствия: локальный запуск не требует отдельного SQL-сервера; совместимость с PostgreSQL проверяется integration-тестами CI. Межпроцессная доставка событий требует отдельного этапа масштабирования.

## ADR-002: SQLite локально, PostgreSQL для CI и развёртывания

- Статус: принято.
- Контекст: разработчику нужен запуск без Docker и отдельного сервера базы данных.
- Решение: локальная среда использует SQLite через `aiosqlite`; CI и необязательный Compose проверяют PostgreSQL.
- Последствия: локальная настройка проще, а PostgreSQL-специфичное поведение остаётся покрыто проверками CI.

## ADR-003: миграции по мере появления доменных моделей

- Статус: принято.
- Контекст: этап 1 создаёт работающий каркас, модели появляются поэтапно.
- Решение: настроить async Alembic на инфраструктурном этапе и добавлять версионированную миграцию вместе с каждой доменной моделью.
- Последствия: пустая база получает служебную версию Alembic и таблицу `users`; последующие этапы добавляют новые таблицы без ручного изменения схемы.

## ADR-004: access token для MVP

- Статус: принято.
- Контекст: этап регистрации должен иметь простую схему авторизации, пригодную для REST и будущего WebSocket.
- Решение: короткоживущий JWT access token, передаваемый в заголовке Bearer; идентификатор токена (`jti`) и временные claims обязательны. Пароли хешируются Argon2id.
- Последствия: backend хранит секрет подписи только в окружении; logout/refresh/revocation и cookie transport отложены. Истечение токена требует повторного входа.

## ADR-005: идемпотентность и cursor history

- Статус: принято.
- Контекст: WebSocket-клиент может повторить отправку после потери ack, а OFFSET становится дорогим на больших историях.
- Решение: уникальный `(sender_id, client_message_id)` в БД; историю сортировать по `(created_at, id)` и продолжать непрозрачным курсором. Текст сначала фиксируется транзакцией.
- Последствия: повтор с тем же содержимым безопасно возвращает исходную запись; конфликтующий повтор отклоняется. Пагинация не требует смещения через уже просмотренные строки.

## ADR-006: WebSocket token в первом событии

- Статус: принято.
- Контекст: стандартный браузерный WebSocket API не позволяет задавать произвольный Authorization header, а token в URL может попадать в access logs.
- Решение: после handshake сервер принимает только `auth.authenticate` с короткоживущим access token и не допускает бизнес-события до успешной проверки. Подключение с неподходящим Origin закрывается.
- Последствия: handshake завершается до auth, поэтому сервер устанавливает короткий timeout и ограничивает размер первого event; клиент должен переподключиться при истечении токена.
